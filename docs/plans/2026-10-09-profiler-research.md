# Build BiBCode's Profiler from proven, cheap parts

BiBCode can meet every requirement inside its ~1% CPU budget by combining five pieces. The first is an out-of-process crash monitor built on **`crash-handler` ≥ 0.8.1 + `minidumper` 0.11.0**, re-executing the same binary as Zed does. The second is a **Breakpad `.sym` pipeline in CI** that keeps shipped binaries stripped while making every minidump and panic symbolicatable offline to function and file:line. The third is a **targeted `sysinfo` sampler** that reads only BiBCode's own process tree every 5 s and feeds a **RESIN-style leak detector** on a "private footprint" metric, not RSS. The fourth is **per-method p95-relative latency flags** with perception-based floors, plus client-side Event Timing/LoAF observers reported over the existing RPC channel. The fifth is an **NDJSON writer behind a bounded channel**, exposed first through a `bibcode diag … --json` CLI and second through an rmcp 3.5 MCP route. On Linux, the sampler cost computed from per-call costs measured in this research is about **0.01–0.02% of one core**, roughly 50× under budget. The one thing that would blow the budget is a full process-table refresh every tick (**42 ms, about 0.85% of a core**). The evidence also forces four adjustments to the decisions already made. The in-process crash handler must be attached once at startup and never toggled. The panic hook must record raw addresses and must not abort. The monitor cannot see crashes in WebKit/WebView2 or in provider CLI subprocesses, so those need OS records and exit-status analysis. A clean-shutdown sentinel is the only way to detect OOM kills and SIGKILL, which produce no minidump. Worktree-deletion diagnostics were **not covered by any of the research notes**. The design below gives them only generic primitives (a slow-operation detector and child-process tracking), which still need dedicated research.

## A crash monitor that is always attached but only sometimes armed

The crash stack is mature and matches the chosen design exactly. `crash-handler` installs the in-process hook. On Linux this is a `sigaction(SA_ONSTACK|SA_SIGINFO)` for six fatal signals, plus an interposed `pthread_create` that gives every thread, including GTK/WebKit ones, an alternate signal stack. On Windows it is an unhandled-exception filter, and on macOS task-level Mach exception ports. `minidumper` carries the crash context over IPC to a monitor process that writes the dump from outside the crashed address space ([crash-handler README](https://github.com/EmbarkStudios/crash-handling/blob/main/crash-handler/README.md), [linux/state.rs](https://github.com/EmbarkStudios/crash-handling/blob/main/crash-handler/src/linux/state.rs)). Zed ships this pattern in production. It spawns `current_exe() --crash-handler <socket>`, retries the client connection every 100 ms, pings every 10 s, and calls `set_ptracer(child)` on Linux ([zed crashes.rs](https://github.com/zed-industries/zed/blob/main/crates/crashes/src/crashes.rs)). This research reproduced the pipeline end to end on Linux x86_64. A stripped binary segfaulted on a thread named `worker-1`. The monitor wrote a **119 KB** minidump, and the process still exited with SIGSEGV. `minidump-stackwalk` against a `dump_syms` store printed `mdtest::crash_here_in_named_function [main.rs : 4]`; without symbols the same frame read only `mdtest + 0x3f0a0`.

**The version pin is not optional.** crash-handler 0.8.0 and older reply `KERN_SUCCESS` to Mach exceptions from inherited ports. On macOS this means a child process spawned after `attach` that hits a hardware fault "never dies … sits at 100% CPU forever". 0.8.1 fixed this on 2026-09-25 ([issue #125](https://github.com/EmbarkStudios/crash-handling/issues/125)). BiBCode spawns provider CLIs, PTYs and git constantly, so anything older than 0.8.1 is disqualifying. The same reasoning rules out `minidumper-child` and `sentry-minidump`, which still pin crash-handler 0.7 ([minidumper-child](https://crates.io/crates/minidumper-child)). Mixing them with 0.8 would also put two `#[no_mangle] pthread_create` symbols in one link.

The user's decision to run the monitor "while the Profiler is on" needs one refinement. **The in-process handler should be attached once at process start and never detached.** Only the monitor child should follow the toggle. The Linux signal handler is effectively one-shot: both `Handled(true)` and `Handled(false)` uninstall it before re-raising. `detach()` restores whatever handlers existed _at attach time_, which silently removes any handler JavaScriptCore installed afterwards ([linux/state.rs](https://github.com/EmbarkStudios/crash-handling/blob/main/crash-handler/src/linux/state.rs)). Detach can itself currently panic on sigaltstack teardown ([PR #118](https://github.com/EmbarkStudios/crash-handling/pull/118)). Ordering also matters on Linux. JSC installs SIGSEGV/SIGBUS handlers _without_ `SA_ONSTACK` and chains to the previous action when it does not handle a fault ([WebKit Signals.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WTF/wtf/threads/Signals.cpp)). If crash-handler attaches first, which is Zed's order, JSC sits on top, handles its own benign VMTraps/Wasm faults, and chains real crashes down. If crash-handler attaches after the webview exists, a benign JSC fault could reach crash-handler and be turned into a fatal crash. Attaching early has one cost, which is an inference from the flags rather than a test: a stack overflow will likely double-fault inside JSC's handler before reaching crash-handler.

The persisted per-environment toggle is read in `main()` only to decide whether to spawn the monitor child; the handler attaches regardless of its value. The concrete shape is therefore as follows. Dispatch `--crash-monitor` in desktop `main()` beside the existing open-url shim, before Tauri, GTK and `tauri-plugin-single-instance` (which would otherwise forward the monitor's argv to the running app and exit). Give the standalone server a plain `fn main` that dispatches the monitor before building the tokio runtime. Attach the handler immediately afterwards. The crash callback reads a `static AtomicBool` and an atomically swappable `Client`; with no client or the flag off, it returns `Handled(false)` so the OS default path, such as systemd-coredump or WER, still runs. One global handler covers both the Tauri host and the in-process server, so the in-process server must not attach its own. The callback runs in a compromised context: no `tracing`, no allocation, no locks. A panic inside it deadlocks on crash-handler's mutex ([issue #82](https://github.com/EmbarkStudios/crash-handling/issues/82)). Two library defaults must be overridden. The monitor's `on_minidump_created` must return `LoopAction::Continue`, because the upstream example and Zed return `Exit`. And a `Client` is dead after one dump, as reported on Linux ([issue #99](https://github.com/EmbarkStudios/crash-handling/issues/99)), so it must reconnect after every dump. One caveat is unavoidable: the `pthread_create` interposer is active merely by linking the crate, even if nothing is attached ([issue #123](https://github.com/EmbarkStudios/crash-handling/issues/123)). "Profiler off" therefore still means crash-handler code sits on every thread creation.

### Panics must be recorded, not converted into crashes

Zed's panic hook ends in `std::process::abort()`, which turns every panic into a minidump and process death ([zed crashes.rs](https://github.com/zed-industries/zed/blob/main/crates/crashes/src/crashes.rs)). BiBCode must not copy that. It runs `panic = "unwind"` deliberately and recovers panics through `catch_unwind` and tokio `JoinError::is_panic()` in many places ([tokio JoinError](https://docs.rs/tokio/latest/tokio/task/struct.JoinError.html)), so aborting would convert recoverable faults into outages. The current profile also makes in-process backtraces worthless. rustc warns that `-Cstrip=symbols` "can affect [backtraces] so negatively as to make the trace incomprehensible" and that crash-reporting programs "should usually avoid" it ([rustc codegen options](https://doc.rust-lang.org/rustc/codegen-options/index.html)). Measured here with rustc 1.97.1, every Rust frame printed `<unknown>` under `strip = "symbols"`, and `RUST_BACKTRACE=full` gave only ASLR-randomized absolute addresses.

The hook should therefore chain to the previous hook and capture up to about 64 instruction pointers with `backtrace::trace`, without resolving them. It maps each IP to `(module debug_id, module name, ip − base)`, then lets unwinding continue. Module bases come from `module_base_address()` on Windows, which is the only OS where the `backtrace` crate returns one ([backtrace-rs](https://github.com/rust-lang/backtrace-rs/tree/master/src/backtrace)), and from `dladdr` plus a startup-cached ELF build-id or Mach-O `LC_UUID` on Linux and macOS. That tuple uses Breakpad's own addressing, so the same `.sym` store symbolicates panics and minidumps. The `dladdr` mapping was not prototyped in this research. The hook runs before the panic runtime under both strategies ([std::panic::set_hook](https://doc.rust-lang.org/std/panic/fn.set_hook.html)), so even a Windows fatal abort, which uses `__fastfail` and bypasses all in-process handlers ([rust std windows/mod.rs](https://github.com/rust-lang/rust/blob/main/library/std/src/sys/pal/windows/mod.rs)), has already sent its record. An optional minidump for the first panic per process is possible via `simulate_signal`, which on Linux bypasses the one-shot handler and is non-destructive. It should be rate-limited, because the ptrace-based dump pauses the whole process.

### What the host handler cannot see, and how to see it anyway

"Subprocess crashes with exact location" splits into three cases with very different reach. **Web content crashes happen in another process.** WebKitGTK's WebKitWebProcess, WKWebView's WebContent and WebView2's renderer all crash outside BiBCode's address space ([webkit2gtk web-process-terminated](https://webkitgtk.org/reference/webkit2gtk/stable/signal.WebView.web-process-terminated.html)). The host can only subscribe to termination: `web-process-terminated` through wry's `WebViewExtUnix::webview()`; wry's macOS-only `with_on_web_content_process_terminate_handler`; and on Windows `ProcessFailed`, whose `FailureReportFolderPath` holds real Chromium minidumps that symbolicate against Microsoft's symbol server ([ICoreWebView2Environment11](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2environment11), [WebView2 process events](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-related-events)). **Provider CLIs, PTYs and git** are not covered by the re-exec monitor at all. For these the server knows the exit status. An unrequested `SIGKILL` is a strong OOM or systemd-oomd signal, because oomd "send[s] SIGKILL to all processes" in its chosen cgroup ([systemd-oomd(8)](https://man7.org/linux/man-pages/man8/systemd-oomd.service.8.html)). Exact crash locations then come from the OS records described next.

The OS records are rich and readable without privilege on most desktops. On systemd Linux, `coredumpctl --json=short list` finds entries, and `journalctl -a -o json MESSAGE_ID=fc2e22bc6ee647b6b90729ab34a250b1 COREDUMP_PID=<pid>` returns a symbolized backtrace in `MESSAGE`. **`-a` is mandatory**, because fields over 4096 bytes are otherwise nulled ([systemd-coredump(8)](https://man7.org/linux/man-pages/man8/systemd-coredump.8.html), [journalctl(1)](https://man7.org/linux/man-pages/man1/journalctl.1.html)). Each frame carries `(module + 0xoffset)`, which can be symbolicated offline. Rust names appear mangled and need `rustc-demangle`. On Windows, Event 1000/1001 give the faulting module, exception code, fault offset, PID and start time, which together identify the process instance. WER LocalDumps needs an elevated installer, because its dump settings are "not supported in the HKEY_CURRENT_USER registry hive" ([WER Settings](https://learn.microsoft.com/en-us/windows/win32/wer/wer-settings), [troubleshoot app crashing](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-application-service-crashing-behavior)). On macOS, `.ips` files are two concatenated JSON objects. `bug_type == "309"` marks a crash, and a frame's address is `usedImages[imageIndex].base + imageOffset`, keyed by image UUID ([Apple: JSON crash report format](https://developer.apple.com/documentation/xcode/interpreting-the-json-format-of-a-crash-report)).

The glue is a **clean-shutdown sentinel**, the same beacon Chrome uses ([Chromium stability.md](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/stability.md)). At startup, durably write `{state:"running", pid, boot_id, exe, version, started_at, oom_kill_baseline}`. Read the baseline from cgroup v2 `memory.events` of a cgroup that outlives the process, such as `user@UID.service`. Its `oom_kill` counter is hierarchical and world-readable, while `/dev/kmsg` is blocked by `dmesg_restrict` ([cgroup-v2 docs](https://docs.kernel.org/admin-guide/cgroup-v2.html), [kernel sysctl](https://docs.kernel.org/admin-guide/sysctl/kernel.html)). On the next start, a leftover `running` state with the same boot ID and a matching OS record means a crash whose record should be harvested; the same state with no record but a higher `oom_kill` count means the process was likely OOM-killed; and a different boot ID means a system crash or power loss. This is the only mechanism that catches SIGKILL, because SIGKILL produces no core and no minidump.

## Stripped binaries stay stripped; CI keeps the symbols

`dump_syms` needs the unstripped artifact, so the CI sequence has to be `tauri build --no-bundle` → dump symbols → strip → `tauri bundle`. The Tauri 2 CLI documents this split ([Tauri v2 CLI](https://v2.tauri.app/reference/cli/)), but whether `tauri bundle` avoids a cargo rebuild on every platform was not verified end to end. Build with `CARGO_PROFILE_RELEASE_STRIP=none` and `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`, the "minimal amount of debug info for backtraces with filename/line number info" ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)). Each OS then needs one adjustment. On **Linux**, run `dump_syms --inlines --store symbols <bin>` on a copy carrying the shipped filename, because the MODULE name comes from the input filename, then `strip --strip-all`. Add `-C link-arg=-Wl,--build-id` if `readelf -n` shows no build-id, since rustc does not guarantee one ([Sentry Rust troubleshooting](https://docs.sentry.io/platforms/rust/troubleshooting)). On **macOS**, set `split-debuginfo = "packed"`, because Cargo's default there is `unpacked` and produces no dSYM. rustc runs `dsymutil` before its own strip step, so the shipped binary stays stripped ([rustc link.rs](https://github.com/rust-lang/rust/blob/main/compiler/rustc_codegen_ssa/src/back/link.rs)). On **Windows**, `-C strip` never suppresses the PDB on MSVC ([rustc linker.rs](https://github.com/rust-lang/rust/blob/main/compiler/rustc_codegen_ssa/src/back/linker.rs)), so run `dump_syms` on the `.exe` with its PDB alongside. `dump_syms` has no aarch64-Windows prebuilt, but `.sym` output is architecture-independent text, so the x64 runner can process arm64 artifacts ([mozilla/dump_syms](https://github.com/mozilla/dump_syms)). Add `--check-cfi` as a guard. In local tests, a `.debug`-only input yielded `FUNC` records but zero `STACK` CFI records, which degrades stack walking silently.

Symbolication is then just `minidump-stackwalk <dmp> <symdir>`, which searches `<debug_file>/<debug_id>/<debug_file>.sym` and can also pull from `--symbols-url` servers such as Microsoft's ([minidump-stackwalk README](https://github.com/rust-minidump/rust-minidump/tree/main/minidump-stackwalk)). Its `--json` output has a documented stable schema, which suits AI harnesses. `.sym` files hold only function names, source paths and unwind data, never user data, so the `<module>/<DEBUGID>/<module>.sym` store can be attached to each GitHub release as planned. A static mirror of the same layout can later serve `--symbols-url`. The `.sym` sizes for the real binaries are unknown. Locally a 4.6 MB toy produced 1.7 MB with `--inlines`, which suggests tens of MB for BiBCode's desktop binary; measure this before choosing release-asset strategy.

## A 5-second sampler costs about 0.02% of a core

The repo already pins `sysinfo 0.39.6`, and the decisive measurement concerns _how_ it is called. On a 32-CPU Linux box with 3,904 process+thread entries, measured in this research:

| Call                                       | Cost per call |
| ------------------------------------------ | ------------- |
| `refresh_processes(All, true)`             | 42.3 ms       |
| `All`, cpu+mem, `.without_tasks()`         | 7.3 ms        |
| `Some(&pids)`, cpu+mem, `.without_tasks()` | ~7 µs per PID |
| `/proc/self/status` read                   | 3.5 µs        |

The full refresh at 5 s intervals is **0.85% of one core**, nearly the whole budget. A targeted refresh of a ~20-PID tree (≈0.3 ms) plus a `without_tasks` rediscovery every 60 s works out to **about 0.01–0.02%**. That is comfortably below Google-Wide Profiling's "less than a few percent" per-machine ceiling, and in the same range as its <0.01% aggregate overhead ([Ren et al., GWP, IEEE Micro 2010](https://research.google/pubs/pub36575/)). It is also far below Pyroscope's ~2–5% for 100 Hz stack sampling ([Pyroscope v1.10 docs](https://archive.grafana.com/docs/pyroscope/v1.10.x/introduction/continuous-profiling/)). Keep one long-lived `System`, because CPU% is a delta and the first sample reads 0. Run refreshes on a blocking thread. Report the profiler's own CPU in every sample and back off (double the interval, skip rediscovery) if a tick exceeds 50 ms. This adopts GWP's rule of ceasing when overhead or failures cross a threshold. Two platform caveats are unmeasured. On Windows, `ProcessesToUpdate::Some` still takes a system-wide Toolhelp snapshot each tick ([sysinfo windows/system.rs](https://github.com/GuillaumeGomez/sysinfo/tree/v0.39.6/src)). On macOS, reading other processes' footprint may need `proc_pid_rusage` rather than `task_info`.

### Leak detection watches the private-memory floor, not RSS

RSS is the wrong input. It counts evictable file-backed pages, shrinks under memory pressure or macOS compression, and on Windows reflects a working set the OS trims. Chromium's "private memory footprint" uses RssAnon + VmSwap on Linux, `private_bytes` on Windows and `phys_footprint` on macOS ([Chromium process_memory_dump.cc mirror](https://gitcode.com/openharmony-tpc/chromium_src/blob/master/base/trace_event/process_memory_dump.cc), [Chromium code review 2875823004](https://codereview.chromium.org/2875823004), [Microsoft Learn PROCESS_MEMORY_COUNTERS_EX](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)). sysinfo's `memory()` returns RSS/WorkingSet, so each OS needs a small native read. The detection logic should borrow from Azure's RESIN, which ran in production for about three years. It sampled every **5 minutes**, aggregated hourly, rejected static thresholds as false-positive generators, reset its "suspicious interval" on 3σ step changes and on drops below the interval start, and classified growth by R² > 0.8 over the most recent **6 hours**. It reported **7 false positives in 291 resolved cases over 14 months**, both from legitimate step-ups after a feature or configuration change ([RESIN, OSDI '22](https://www.usenix.org/system/files/osdi22-lou-resin.pdf)).

Adapted to one host, the recommended defaults are engineering choices, since no published per-app MB/h standard exists. Downsample the 5 s samples to **1-minute medians** (360–720 points in memory) and skip a **10–15 minute warm-up**. Track a rolling 5–10 minute _minimum_ as the "floor", so JS-heap sawtooth and allocator burst-then-retain raise peaks without raising the floor. Flag **"suspect"** when the Theil–Sen slope, robust to 29.3% outliers ([Theil–Sen](https://en.wikipedia.org/wiki/Theil%E2%80%93Sen_estimator)), exceeds **max(10 MB/h, 2% of baseline per hour)** for an hour and a one-sided Mann–Kendall test is significant at Z > 2.33. Flag **"likely leak"** after 6 h of growth with R² > 0.8, or after ≥ 50% and ≥ 200 MB of growth since baseline. Require two or three consecutive hits before alerting, and alert at most once per process per 6 h. jemalloc's 10 s dirty-page decay ([jemalloc(3)](https://jemalloc.net/jemalloc.3.html)) disappears inside the 1-minute medians. glibc arena retention can form a plateauing staircase ([sourceware bug 30769](https://sourceware.org/bugzilla/show_bug.cgi?id=30769)), which RESIN-style resets absorb. Record the allocator in the telemetry header so analysts can discount it.

## Slow responses are judged against each method's own p95

Latency is right-skewed. The DDSketch authors observe that an endpoint's mean sits nearer p75 than p50 ([Masson et al., PVLDB 2019](https://www.vldb.org/pvldb/vol12/p2195-masson.pdf)). The SRE book warns that a 100 ms average can hide 1% of requests taking 5 s ([Google SRE Book](https://sre.google/sre-book/monitoring-distributed-systems/)). Mean + kσ is therefore inflated by the outliers it is meant to catch. The learned baseline should be a percentile. Google's tail-latency work triggers corrective action once a request exceeds "the 95th-percentile expected latency for this class of requests" ([Dean & Barroso, The Tail at Scale](https://www.barroso.org/publications/TheTailAtScale.pdf)).

The rule the user asked for, with no fixed default threshold, keys on `(method, outcome)`, so slow errors are tracked separately as the SRE book advises. It keeps a ring of six 5-minute log-bucketed histograms. Once at least 100 samples exist, it flags `duration > max(3 × p95, floor)`. The floor is **250 ms** for interactive methods, just above INP's 200 ms "good" ceiling ([web.dev INP](https://web.dev/articles/inp)), and **1 s** for background work. Two always-on absolute tiers at **1 s and 10 s**, Nielsen's flow and attention limits ([NN/g response times](https://www.nngroup.com/articles/response-times-3-important-limits/)), keep a chronically slow method from normalizing its own baseline. The constants 3×, 100 samples and the floors are design choices derived from these sources, not quoted values. Exclude the current interval from the baseline so a burst cannot raise its own threshold. Check _in-flight_ requests on the diagnostics tick so hangs are flagged before they complete. When many methods trip at once, emit one "saturation" event instead of N. `hdrhistogram` records in constant time at 3–6 ns ([docs.rs hdrhistogram](https://docs.rs/hdrhistogram/latest/hdrhistogram/)), but it would be a new dependency. A fixed array of ~100 log buckets per method also suffices at a 3× multiplier.

### Client unresponsiveness needs engine-specific instruments

The three Tauri engines differ sharply in what they expose. WebView2 tracks Edge Stable ([WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)) and has everything: Long Tasks, LoAF with script attribution, Event Timing and `performance.memory`. No WebKit build has Long Tasks, LoAF or a JS-heap API ([MDN browser-compat-data](https://github.com/mdn/browser-compat-data)). Event Timing is on by default only from **WebKitGTK 2.52** ([UnifiedWebPreferences.yaml @ webkitgtk-2.52.0](https://raw.githubusercontent.com/WebKit/WebKit/webkitgtk-2.52.0/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml)) and Safari 26.2. The client should therefore gate each observer on `PerformanceObserver.supportedEntryTypes` and report the capability set with every batch. Where LoAF is missing it should run a 250–500 ms `setTimeout` drift heartbeat, treating more than 50 ms late as a stall, which matches LoAF's 50 ms definition ([Chrome LoAF](https://developer.chrome.com/docs/web-platform/long-animation-frames)). The heartbeat is suspended while the document is hidden. A perpetual rAF loop would keep the webview from idling, so reserve it for explicit profiling sessions. Keep Event Timing's default 104 ms threshold ([MDN PerformanceEventTiming](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceEventTiming)), never ship React's profiling build ([react.dev Profiler](https://react.dev/reference/react/Profiler)), and send aggregated per-window summaries over the existing RPC channel, not raw entries. On WebKit, memory must come from the Rust side, by sampling the WebKitWebProcess/WebContent PIDs.

### Remote mode works because only durations cross the wire

For remote servers over SSH or relay, never subtract timestamps taken on different machines. Have the server put `serverMs` (handler time, `Instant`-based) and `queuedMs` into each RPC response, an in-band equivalent of `Server-Timing`, since WebSocket frames carry no headers. The client then computes `transport ≈ rtt − serverMs − queuedMs` with monotonic `performance.now()` ([MDN performance.now()](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)), and `render ≈ painted − received` via a double-rAF after the state update. Tag server flags and client flags with the same `requestId`, so one record shows whether the server, the network or the renderer was slow. This works without any clock synchronization. Discard samples spanning a hidden document or system sleep, because `performance.now()` stops during sleep except on Windows.

## Storage, harness access and privacy share one source of truth

The writer design follows tokio's own guidance. `tokio::fs` dispatches every operation to `spawn_blocking` at "serious" cost and recommends batching into a `std` `BufWriter` instead ([docs.rs tokio::fs](https://docs.rs/tokio/latest/tokio/fs/index.html)). Hot paths call `try_send` on a bounded channel of 2048 events, which never awaits ([tokio Sender::try_send](https://docs.rs/tokio/latest/tokio/sync/mpsc/struct.Sender.html#method.try_send)), and count drops in an `AtomicU64`. Drops are written into the file as `telemetry_dropped` events, so data loss is visible. One writer thread serializes batches to a 64 KiB `BufWriter`, flushes every 1–5 s, rotates at 10 MiB, and calls `sync_data()` only on rotation and shutdown. Implement rotation directly in about 30 lines. `tracing-appender` has no size rotation ([docs.rs tracing-appender](https://docs.rs/tracing-appender)), and `file-rotate` silently discards data when the directory becomes inaccessible ([docs.rs file-rotate](https://docs.rs/file-rotate/latest/file_rotate/)). At ~17k sample events per day of ~300 B, the stream is **~5 MB/day, ~35 MB per 7 days**. The rest of the 256 MB cap is left for minidumps, which measured 35–119 KB here, and their JSON sidecars. A torn final line is the worst crash outcome, and readers skip it. All of this extends the existing `apps/server/src/diagnostics/` module, which already holds monitor, history, trace and attribution code, rather than creating a parallel store.

Expose that one query layer twice, CLI first. `bibcode diag snapshot|events|crashes|symbolicate --json [--follow --duration 30s --limit N]` needs no harness configuration, works identically in Claude Code and Codex, and reaches remote hosts as `ssh host bibcode diag …`. Bound every follow, because an unbounded one hangs an agent's shell. The MCP layer uses **rmcp 3.5.1**, which implements the **2026-07-28** spec that removed sessions, the `initialize` handshake and `resources/subscribe` ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). It also keeps 2025-11-25 compatibility, so do not narrow `supported_protocol_versions`. Codex itself depends on rmcp ([openai/codex Cargo.toml](https://github.com/openai/codex/blob/main/codex-rs/Cargo.toml)). Mount `StreamableHttpService` with `nest_service` behind BiBCode's existing bearer middleware, the pattern of the SDK's `simple_auth_streamhttp.rs` ([rust-sdk examples](https://github.com/modelcontextprotocol/rust-sdk/blob/main/examples/servers/src/simple_auth_streamhttp.rs)). Static bearer tokens are spec-permissible because MCP authorization is optional ([MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). Claude Code (`--header`, `${VAR}` in `.mcp.json`) and Codex (`bearer_token_env_var`) both accept them ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp), [Codex MCP docs](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)). Three settings must be explicit: `with_legacy_session_mode(false)`; `enforce_origin_validation()`, because the spec requires 403 on an invalid Origin ([Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)) while rmcp disables the check by default; and the loopback-only `allowed_hosts` default, which an `ssh -L` tunnel preserves for remote servers. Keep tools read-only, mint a diagnostics-scoped token, and paginate under Claude Code's **25k-token** output cap and Codex's **60 s** tool timeout.

Privacy belongs at the collector, not at each transport. Minidumps contain stack memory that can hold prompts, tokens and paths. Keep them local and export them only on explicit request, and strip user strings from panic messages as Zed does. Redact secrets and home paths, strip ANSI and control characters, and truncate fields before an event reaches the NDJSON file. Return logs as `structuredContent` with tool descriptions stating that the content is untrusted application data. The MCP spec obliges servers to "sanitize tool outputs" ([MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)), and provider output that BiBCode logs is a live prompt-injection vector.

### Risks that need a smoke test before shipping

| Risk                                     | Why it matters                                                                                                                                            | Mitigation                                                                   |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Windows arm64                            | A shipped target, but minidump-writer marks it "unimplemented" ([minidump-writer](https://github.com/rust-minidump/minidump-writer)); it compiles locally | Disable dumps there until a runtime test passes; panic records still work    |
| macOS and Windows dump paths             | Only Linux x86_64 was run end to end                                                                                                                      | CI smoke test that crashes a test binary per OS and symbolicates it          |
| ptrace in containers                     | Yama scope ≥ 2, seccomp or a missing `SYS_PTRACE` blocks the Linux monitor's attach                                                                       | Probe at startup; record "dumps unavailable" in the capability header        |
| Signals hitting the monitor              | The re-exec child shares the process group and console, so Ctrl-C kills it too                                                                            | `setpgid` / `CREATE_NEW_PROCESS_GROUP`; ignore SIGINT/SIGTERM in the monitor |
| WebView2 overriding the exception filter | Unverified whether the runtime calls `SetUnhandledExceptionFilter` in the host                                                                            | Log the active filter after webview creation                                 |
| Old WebKit                               | WebKitGTK ≤ 2.50 and pre-26.2 WKWebView lack Event Timing                                                                                                 | Heartbeat fallback; capability tagging                                       |
| Worktree deletion                        | No research collected                                                                                                                                     | See conclusion                                                               |

## Conclusion

The most useful shift from this research is that "crash profiler" is the wrong mental model for BiBCode. Most failures that users experience occur in processes the profiler does not own (WebKit content, provider CLIs, git) or in ways no in-process handler can catch (OOM SIGKILL, `__fastfail`, power loss). The minidump monitor is the precise tool for the narrow case of BiBCode's own native faults. The sentinel, exit-status analysis and OS crash records cover everything else, so they deserve equal implementation priority. A second implication is that the user's two "lightweight" decisions, stripped binaries and a toggleable monitor, are both compatible with high-fidelity diagnosis only if the CI symbol pipeline and the attach-once handler land in the same change. Each half is useless without the other.

Worktree-deletion problems remain the open item. None of the collected sources address them. Treat the following as untested inference until dedicated research covers Windows file locking and `remove_dir_all` semantics. The pieces built here already provide most of the instrumentation: a slow-operation detector keyed by operation name (`worktree.remove`) under the same p95 rule; the tracked child-process tree, to report which BiBCode-owned PIDs still have a cwd or open handle under the target path; and the NDJSON event stream, to record each attempt's error code and retry. The adaptive thresholds also need real traffic before they become meaningful. Ship the first release with the absolute 1 s / 10 s tiers active and the relative tier in log-only mode, then promote it once each method has accumulated its 100-sample baseline across real sessions.
