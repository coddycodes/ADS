## 1. Summary

**Q1: internal browser.**

- BiBCode already has one on desktop: native Tauri child webviews. Primary-clicking
  an http(s) link in chat already opens it, as do `.html`/`.htm`/`.pdf` file links.
- The terminal shows a choice menu for loopback URLs only. It sends file paths to
  the editor on the server, and it can never put them in the browser.
- The brainstorming companion is a live, keyed server on the server's
  `localhost`. For it to land in the internal browser by default on every
  topology, BiBCode needs three things:
  1. one link router with a setting, applied to chat, terminal, and OSC 8 links;
  2. a hook (`BRAINSTORM_OPEN_CMD`/`BROWSER`) so that a `--open` that today runs on
     the server host instead opens a preview tab;
  3. a way to reach server-loopback ports from the client. Today SSH and relay
     resolve `localhost` on the client. LAN and WSL work only when the dev server
     binds a non-loopback address.
- For the third item, the best fit is an authenticated preview gateway on the
  server: an HTTP and WebSocket reverse proxy that gives each target its own
  origin. It works on SSH, relay, LAN, WSL, and in browser mode.
- Orca's per-session SOCKS routing preserves origins exactly. In Tauri, though,
  the proxy is per profile rather than per webview, it needs a Cargo feature on
  macOS, and it inherits the Linux child-webview geometry problem. Keep it as an
  optional later upgrade.

**Q2: mobile emulators.** These are not local-only, and ref-preview proves it: its
Devices feature streams server-hosted simulators to the client through an
authenticated `/api/device-hub/*` proxy.

- **Android** works remotely on any server OS with hardware virtualization
  (`-no-window`, adb, scrcpy-server, emulator gRPC).
- **iOS Simulator** on a macOS server is feasible with caveats. Frames come from
  CoreSimulator's framebuffer, so no Screen Recording permission is needed. Input,
  however, needs private SimulatorKit APIs (idb/serve-sim), and the server must run
  under a logged-in user.
- The binding constraint is BiBCode's transport. RPC streams are stop-and-wait, so
  frames per second is at most 1/RTT. Payloads are JSON-only, and neither SSH nor
  the relay carries UDP.
- Start with JPEG frames on a conflating stream. Then move to H.264 over a
  dedicated authenticated media socket, which needs a design document.

### 2.2 BiBCode today

**Host**

- **Tauri version and features.** Tauri 2.11.5 with `unstable`, `devtools`, and `image-png` (`bibcode/Cargo.toml:59`, the workspace manifest).
- **Tabs.** A tab is a `WebviewBuilder` attached with `window.add_child` to `main` (`bibcode/apps/desktop/src-tauri/src/preview/host.rs:708-835`).
  - Navigation is limited to `about:blank` and http(s) (`host.rs:774-776`).
  - There is **no `on_new_window`** handler (`host.rs:773-816`).
  - Each tab uses an isolated profile: `data_store_identifier` on macOS 14 or later, otherwise one shared `<app_data>/preview-profile` (`host.rs:713-721,819-827`). macOS below 14 fails closed (`host.rs:684-706`).

- **Server side.** The server is a state store only.
  - `PreviewManager` holds tab state (`bibcode/apps/server/src/preview/mod.rs:148-405`).
  - The RPCs are `preview.*` and `previewAutomation.*` (`bibcode/apps/server/src/production/workspace_preview.rs:39-49`).

**Remote resolution, verified in `bibcode/apps/web/src/browser/browserTargetResolver.ts` (92 lines)**

- `resolveBrowserNavigationTarget`:
  - passes `url` targets through unchanged (`:36-43`);
  - for `environment-port` targets, throws the "planned authenticated preview gateway" error when the environment host is not private-network (`:47-50`);
  - otherwise rewrites the URL to `<environment host>:<port>` (`:52-68`).
- `resolveDiscoveredServerUrl`:

| BiBCode env  | Neither `BROWSER` nor `BRAINSTORM_OPEN_CMD` is set for providers or terminals                                                                                                                                                                      | search of `bibcode/apps/server/src` and `bibcode/apps/desktop`          |

**Why it fails remotely today (Windows client, macOS server)**

1. A click on the URL in chat opens `http://localhost:PORT/?key=…` in the child webview. That is the **client's** localhost (§2.2).
2. Ctrl-clicking it in the terminal shows the same menu with the same problem.
3. `--open` runs `open` on the macOS server, which launches Safari in the server's GUI session or does nothing headless. It never reaches the client.
4. The port-discovery card shows `127.0.0.1:PORT` without `?key=`, so it returns 403.
5. `/api/assets` cannot stand in. It is static, limited to the workspace (`/tmp` sessions are outside it), and drops the frame template, `helper.js`, the WebSocket, and live reload **[inferred]**.

Even locally, `--open` goes to the system browser rather than the internal one.
The internal browser is reached locally only by clicking the link in chat, or by
the agent calling `preview_open`, which hits the Tauri automation stub caveat
above.

**What any remote fix must satisfy for this companion:** the key cookie must
reach the right origin; the page must be served at the origin root, because it
redirects to `/` and sets `Path=/`; Host and Origin on the WebSocket upgrade must
be consistent; and it must be top-level, never framed.

### 2.4 Remote options for internal-browser routing by default

**(a) A SOCKS-routed profile per environment, the Orca model**

- **Feasibility in Tauri.** The API exists, but it is not per webview.
  - `WebviewBuilder::proxy_url(http|socks5)` (`tauri-2.11.5/src/webview/mod.rs:1002-1013`) is parsed into wry `ProxyConfig::{Http,Socks5}` (`tauri-runtime-wry-2.11.4/src/lib.rs:4477-4490`) and applied with `with_proxy_config` (`:5047-5051`).
  - On every engine, wry attaches the proxy to the **profile or data store**, not to the view:

    | Engine    | Where wry applies the proxy                                                                                                         | Consequence                                                                                                                                                                                                                                     |
    | --------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | WebView2  | It appends `--proxy-server=…` to the _environment's_ browser arguments (`wry-0.55.1/src/webview2/mod.rs:304-317`).                  | Webviews with different environment options must use different `data_directory`s (`wry-0.55.1/src/web_context.rs:40-44`). Tauri keys contexts by `data_directory` (`tauri-runtime-wry-2.11.4/src/lib.rs:4793`).                                 |
    | WebKitGTK | `website_data_manager.set_network_proxy_settings(Custom, …)` with an empty ignore list (`wry-0.55.1/src/webkitgtk/mod.rs:267-278`). | Applies to every webview on that WebContext.                                                                                                                                                                                                    |
    | WKWebView | KVC `proxyConfigurations` on the `WKWebsiteDataStore` (`wry-0.55.1/src/wkwebview/mod.rs:326-343`).                                  | Applies to the data store. The block is gated on `#[cfg(feature = "mac-proxy")]` (`:9-10,326`), which Tauri exposes as `macos-proxy` (`tauri-2.11.5/Cargo.toml:112`). **BiBCode does not enable it**, so today `proxy_url` is ignored on macOS. |

  - **[inferred]** wry passes no bypass list. Chromium bypasses loopback implicitly, which is why Orca adds `<-loopback>`, so on WebView2 `localhost` would skip the proxy. The fix is to build the full argument string through `additional_browser_args`, which is Windows-only and replaces wry's defaults, so they must be re-added (`tauri-2.11.5/src/webview/mod.rs:945-956`).
  - WebKitGTK's localhost handling with an empty ignore list, and WKWebView's handling of `proxyConfigurations` for loopback, are **unverified**.
  - BiBCode's single shared `preview-profile` (`host.rs:713-721`) would therefore have to become one profile per environment. That matches Orca's routed partitions keyed by host (`orca/src/main/browser/browser-route-identity.ts:19-50`).
- **SOCKS endpoint.**
  - SSH: add `-D 127.0.0.1:<port>` to the desktop's ssh process (`ssh.rs:554-590`).
  - Relay, LAN, and WSL: a new tunnel over RPC, like Orca's `network.browserTunnel`. That is a new protocol surface.
- **Security.**
  - The page keeps its true origin (`localhost:PORT`), so cookies, OAuth redirects, and CORS behave exactly as they do locally.
  - Per-environment profiles also isolate cookie jars per server.
  - A loopback SOCKS listener on the client is reachable by any local process. Orca makes it CONNECT-only on loopback (`orca/src/main/browser/remote-browser-socks-server.ts:60,104-107`).
  - DNS-prefetch and WebRTC leaks need policy, as they did for Orca.
- **Topologies.** SSH is cheap through `-D`. Relay, LAN, and WSL need the RPC tunnel. **Browser mode gets nothing**, because there is no webview.
- **Blockers.**
  - Linux child-webview geometry (§2.6).
  - The macOS feature flag.
  - The WebView2 bypass list.
  - Profile management per environment.

**(b) An authenticated server-side preview gateway (recommended primary)**

This is the "planned authenticated preview gateway" named in both
`bibcode/apps/web/src/browser/browserTargetResolver.ts:49` and
`ref-preview/apps/web/src/browser/browserTargetResolver.ts:31-35`. It is an HTTP and
WebSocket reverse proxy on the BiBCode server to server-loopback ports.

- **Template.** ref-preview's `DeviceHubProxy` already implements the pattern for a single upstream (`ref-preview/apps/server/src/device/DeviceHubProxy.ts`):
  - path allowlists for HTTP and WebSocket (`:39-62`, enforced at `:196`);
  - authentication by cookie or a short-lived `wsTicket`, because `<img>` and WebSocket cannot set headers (`:83-108`);
  - `host`, `cookie`, `authorization`, and `dpop` are dropped before forwarding (`:65-78`);
  - a wildcard route (`:233`).
  - BiBCode already mints WebSocket tickets (`/api/auth/websocket-ticket`, `bibcode/apps/server/src/auth/http.rs:36-54`).
- **Origin isolation is the hard part.**
  - A path prefix such as `/preview/5173/…` breaks apps that use absolute paths. The brainstorm companion redirects to `/` and sets `Path=/`.
  - It would also put the previewed app on the **BiBCode UI origin**, giving it the session cookie (`SameSite=Lax`, `bibcode/apps/server/src/auth/http.rs:96-101`) in browser mode.
  - The gateway therefore needs **one origin per target**. Candidates:
    - a dedicated listener port on the server. SSH needs a second `-L`, and the relay needs a second ingress;
    - `<capability>.preview.<host>` subdomains. The relay needs wildcard DNS and certificates; locally, `*.localhost` resolves to loopback in Chromium **[inferred; WebKit engines unverified]**.
- **Auth.** Use a short-lived signed capability in the first request (like `/api/assets`), exchanged for a cookie scoped to the target origin. Require `orchestration:read` at minimum to mint it (`bibcode/apps/server/src/auth/scope.rs:22`). Never forward the BiBCode session or authorization upstream.
- **Upstream rewrite.**
  - Rewrite `Host` to `localhost:PORT` and rewrite `Origin` on upgrades. Over the relay the browser sends `https://…`, which fails the companion's `Origin === "http://"+Host` check unless the gateway rewrites it.
  - Strip or rewrite `Set-Cookie` domains.
  - Allow only loopback targets, and only ports the server's scanner discovered or the user or agent explicitly opened.
- **Topologies.**
  - SSH, relay, LAN, and WSL all work, because the gateway is just HTTP on the server.
  - **Browser mode also gains a usable preview**, either a top-level tab or later an iframe on the gateway origin.
  - On E2EE profiles over plain HTTP, gateway traffic travels outside Noise, just as assets do today (`bibcode/docs/architecture/remote.md:243-251`).
- **Costs.**
  - The origin changes: an app that hard-codes `http://localhost:3000` in absolute URLs, OAuth redirect URIs, or CORS allowlists breaks. Option (a) or (d) avoids this.
  - A new security-sensitive HTTP surface.
  - Streaming through the server's Tokio runtime. Bound per-connection buffers and concurrency to avoid amplifying backpressure **[inferred]**.

**(c) Signed asset URLs (exists; static only)**

- **What exists.**
  - `assets.createUrl` → `GET /api/assets/{token}/{*path}`: an HMAC token with purpose `"asset"`, 1 h TTL, and a `WorkspaceSiblings` claim for `.html`/`.htm`/`.pdf` (`bibcode/apps/server/src/assets/mod.rs:12-23,84-86,113-131,295-315`).
  - It is limited to the thread's workspace (`bibcode/apps/server/src/workspace/rpc.rs:1105-1145`) and capped at 10 MiB (`bibcode/apps/server/src/production/runtime.rs:575-623`).
  - It travels over every topology, relative to `httpBaseUrl` (`bibcode/packages/client-runtime/src/state/assets.ts:38-40`).
- **CSP and sandbox gap (verified).**
  - The asset response sets only `content-type`, `cache-control`, and `nosniff` (`bibcode/apps/server/src/production/http_routes.rs:459-482`).
  - The route has no session check (`:277`).
  - The CSP header exists only on the static UI handler (`bibcode/apps/server/src/http.rs:758`).
  - So agent-written HTML runs **on the BiBCode UI origin with no sandbox**. In browser mode its scripts could call authenticated `/api` with the `SameSite=Lax` cookie **[inferred risk]**. Desktop is shielded only because the preview profile is isolated.
  - ref-preview solves this with a single header, `sandbox allow-scripts allow-forms allow-popups` (`ref-preview/apps/server/src/http.ts:56-61`), which gives the document an opaque origin.
- **Fit.** It covers static HTML artifacts and PDFs. It cannot serve the brainstorm companion, which is live and keyed, or any dev server.
- **Possible extension.** An "artifact" claim for files outside the workspace, such as `/tmp` session dirs, granted explicitly per file, like Orca's `orca-preview://` grants (`orca/src/main/browser/doc-preview-grant-registry.ts:5-42`).

**(d) SSH `-L` per discovered port**

- **How.** The desktop already spawns `ssh -N -L <local>:127.0.0.1:<remote>` per environment (`ssh.rs:554-590`). Add a same-number forward, `-L PORT:127.0.0.1:PORT`, on demand when a loopback URL is opened. This needs a new ssh process per port or a ControlMaster `-O forward`.
- **Security.** The page keeps its true origin, so the brainstorm cookie and Origin check work unchanged. The forward is loopback-only on the client, and any local process can reach it while it exists.
- **Topologies.** SSH only. Relay, LAN, WSL, and browser mode get nothing. If the client port is already in use, the number cannot be preserved, and Orca shows remapped forwards miss **[inferred]** (`orca/src/main/ssh/ssh2-port-forward-provider.ts:24-29`).
- **Fit.** A cheap SSH-only complement to (b) that preserves the origin. It needs no new server protocol and is desktop-only.

**Option matrix**

|                   | Origin preserved | SSH        | Relay            | LAN/WSL          | Browser mode                            | New surface                  | Main risk                                          |
| ----------------- | ---------------- | ---------- | ---------------- | ---------------- | --------------------------------------- | ---------------------------- | -------------------------------------------------- |
| (a) SOCKS profile | yes              | yes (`-D`) | needs RPC tunnel | needs RPC tunnel | no                                      | desktop profiles, tunnel RPC | engine proxy quirks, Linux geometry, macOS feature |

### 2.6 Tauri constraints that gate everything above

- **Linux child webviews.**
  - Tauri builds Linux children with `build_gtk(default_vbox)` (`tauri-runtime-wry-2.11.4/src/lib.rs:5226-5237`).
  - wry's `set_bounds` moves a webview only under `x11` or a `gtk::Fixed` parent (`wry-0.55.1/src/webkitgtk/mod.rs:853-875`).
  - BiBCode has no Fixed or reparent workaround (none in `bibcode/apps/desktop/src-tauri/src/preview/platform/linux.rs`), and `is_supported()` returns `true` off macOS (`host.rs:696-706`).
  - **[inferred, needs runtime check]** On Linux the overlay is laid out by the Box, not by `desktop_preview_set_bounds`. Upstream tracks this as tauri#10420, #16132, and #15656; fix PR #16133 was closed unmerged.
- **Iframes.** Not viable. The CSP has no `frame-src` (`bibcode/apps/desktop/src-tauri/tauri.conf.json:26`). Tauri cannot tell iframe IPC from window IPC on Linux (https://v2.tauri.app/security/capabilities/). Many targets, the companion included, refuse framing.
- **DevTools.** Available in release builds, but it uses private API on macOS, which is not App Store safe (`tauri-2.11.5/src/webview/mod.rs:1110-1118,1989`).
- **Screenshots.** No Tauri API exists. BiBCode's per-platform native code is the right approach (`bibcode/apps/desktop/src-tauri/src/preview/platform/{windows,macos,linux}.rs`).

**iOS Simulator details**

- **Frames.** `simctl io` and idb read CoreSimulator's virtual-framebuffer IOSurface (`idb/FBSimulatorControl/Framebuffer/FramebufferSurface.swift:42,60`). That needs no Screen Recording TCC permission **[inferred]**.

- **Input.** Requires private SimulatorKit HID. idb's `SimDeviceLegacyHIDClient` "has moved between frameworks across Xcodes" (`idb/FBSimulatorControl/HID/SimulatorIndigoHIDClient.swift:13-47`), and `simctl` has no tap command **[inferred]**.
- **Live video.** Needs idb `video_stream` (`idb/proto/idb.proto:69,907-929`). `recordVideo` only writes a file **[inferred]**.
- **Session.** Run as a logged-in user's LaunchAgent. BiBCode's service bootstraps into `gui/<uid>` (`bibcode/apps/server/src/service_manager/manager.rs:281,346`). An SSH-launched server runs in a `StandardIO` session, which is plausible but not guaranteed by Apple (TN2083, https://developer.apple.com/library/archive/technotes/tn2083/_index.html).

None of these targets is LOCAL-ONLY by nature. BiBCode has no emulator code: a
search for `simctl|xcrun|scrcpy|adb` under `bibcode/apps/` and
`bibcode/packages/` finds nothing.

### 3.4 Constraints

- **Permissions.**
  - No macOS Screen Recording grant as long as frames come from the framebuffer.
  - Capturing a window through ScreenCaptureKit would need an interactive grant that MDM cannot pre-approve (https://support.apple.com/guide/deployment/privacy-preferences-policy-control-payload-dep38df53c2a/web).
- **Private APIs.**
  - iOS input (idb HID / DTUHID) breaks across Xcode releases.
  - idb `README` says it uses "Private Frameworks that are used by Xcode".
  - The scrcpy wire protocol has "no backward or forward compatibility" (`scrcpy/doc/develop.md:118-124`), so pin the jar version.
- **Virtualization.**
  - Android needs VT-x, AMD-V, or Apple silicon on bare metal, or exposed nested virtualization.
  - There is a source disagreement: Google's container README says nested virtualization works on AWS bare metal, Azure Dv3/Ev3, and GCE with reduced performance. Android's acceleration page says "can't run … inside another VM".
- **UDP.** Neither SSH `-L` nor the Cloudflare relay carries it. WebRTC needs TURN, so prefer WebSocket media.
- **Exposure.**
  - Keep adb (5037), emulator gRPC (token in `pid_<PID>.ini`), and idb_companion on loopback. Proxy them through the BiBCode server.
  - `adb -a` is unencrypted (`scrcpy/doc/tunnels.md`).

## 5. Recommendations

Under `AGENTS.md`, a new architectural decision needs an approved design document
before implementation: new protocol surface, runtime topology, or a security
boundary. That applies to the **preview gateway**, a **media socket**, a
**per-profile SOCKS proxy plus tunnel RPC**, and the **emulator subsystem**. Phase
0 changes behaviour within existing boundaries, but it still needs living-doc
updates and a `UI.md` review.

### Phase 0: bug-level and policy changes (no new architecture)

1. **Sandbox agent HTML on `/api/assets`.** Add ref-preview's `content-security-policy: sandbox allow-scripts allow-forms allow-popups` to HTML responses and `default-src 'none'; style-src 'unsafe-inline'; sandbox` to SVG.
   - _Trade-off:_ an artifact that uses `localStorage` or cookies loses them, because the document gets an opaque origin. This closes the same-origin script risk in browser mode at almost no cost.
2. **One link router and a setting.** Add `browserLinkTarget` to the contracts settings, then:
   - route chat, terminal (plain Ctrl/Cmd-click), OSC 8 (`linkHandler`), and file links through it;
   - make a modifier invert the target;
   - send `.html` paths in the terminal to the browser, not the editor;
   - add `on_new_window` so popups in previews become tabs and `_blank` in the main window goes to `openExternal`.

   _Trade-off:_ the default (see open questions) changes muscle memory for one surface or the other. This removes every "nowhere" row.

3. **Resolve before opening.** Pass chat and terminal loopback URLs through `resolveDiscoveredServerUrl`. Stop swallowing the gateway error: when the environment is remote and the target cannot be reached, show an actionable notice ("This address is on <server>; open it via SSH forward or the preview gateway") instead of loading the client's localhost.
   - _Trade-off:_ LAN and WSL improve now, while SSH and relay only become honest. Still better than silently wrong content.
4. **Make agent `preview_open` succeed on Tauri.** Report a minimal `automation.status` instead of rejecting, so the agent tool that is meant to put artifacts in the browser does not report failure **[inferred bug]**. Correct `overview.md:36-38` in the same change.
5. **Attribute ports to terminals and threads** (fix `"terminal": null`). This enables a "dev server from this thread" card.
6. **Runtime-check the Linux preview geometry.** If it is broken, either gate `features.preview` on Linux or plan a `gtk::Fixed` mount. Add an integrated-browser section to `docs/testing/`.

### Phase 1: remote reach (design document first)

7. **Preview gateway design (option b).**
   - Base it on ref-preview's `DeviceHubProxy`: allowlist, cookie or ticket auth, hop-by-hop and credential stripping.
   - Decide **one origin per target**: a dedicated listener port, or capability subdomains.
   - Specify Host and Origin rewriting, `Set-Cookie` handling, target admission (loopback only, discovered or explicitly opened), concurrency and backpressure limits, and the E2EE plaintext caveat.

   _Trade-off:_ it changes the page origin, which breaks apps that hard-code `localhost` origins or OAuth redirects. In exchange it is the only option that covers SSH, relay, LAN, WSL, **and browser mode**. Its HTTP+WS proxy core can later carry device streams too, as ref-preview's does.

8. **Open-URL hook.** Inject `BRAINSTORM_OPEN_CMD` and `BROWSER` into provider and terminal environments, pointing at a BiBCode command that calls `preview.open` for the owning thread. It can reuse the per-launch MCP credential (`bibcode/apps/server/src/production/provider_runtime.rs:965-988`) or a new `bibcode open-url` subcommand.
   - With 7 in place, `start-server.sh --open` lands the companion in the internal browser on every topology.
   - _Trade-off:_ this adds a CLI and credential path for agents to call. `BRAINSTORM_OPEN_CMD` is run through a shell with a JSON-quoted URL (`server.cjs:540`), so the command must treat its argument as data.
9. **Optional: SSH same-port `-L` (option d)** for SSH users who need exact origins. It is desktop-only and small, but it can collide with ports already in use on the client.

### Phase 2: fidelity (design document first, only if Phase 1 falls short)

10. **SOCKS profile per environment (option a).** Requires:
    - the `macos-proxy` feature (macOS 14 or later);
    - one `data_directory` or `data_store_identifier` per environment;
    - WebView2 `additional_browser_args` with `<-loopback>`;
    - `ssh -D` for SSH and a tunnel RPC for the other topologies;
    - DNS-prefetch and WebRTC leak policy;
    - working Linux geometry.

    _Trade-off:_ the highest fidelity, preserving origin, cookies, and OAuth, at the highest cost. It does nothing for browser mode.

11. **Picker, annotation, and automation parity**, through a JS-injection engine. WebView2's CDP is an option on Windows only. This is high effort, and the payoff is agent-driven testing.

### Phase 3: emulators (design document first)

12. **Android first.** On the server, Rust drives `emulator -no-window`, adb, and either emulator gRPC (`streamScreenshot`, `sendTouch`) or a pinned scrcpy-server jar. Start with JPEG frames on a `LatestStream` RPC plus typed input RPCs.
    - This works everywhere today at 8–17 Mb/s and about 150–200 ms tap-to-photon on a WAN.
    - _Trade-off:_ not smooth, but it needs no new transport.
13. **Media socket design.** H.264 over a dedicated authenticated binary WebSocket, decoded with WebCodecs in a worker, with feature detection and fallback to 12, at about 1–3 Mb/s and 80–110 ms. Alternatively, reuse the gateway's WS proxy core.
    - _Trade-off:_ a new runtime topology and a carve-out to the typed-RPC rule.
14. **iOS later.** `xcrun simctl` for lifecycle, screenshots, and `openurl`. idb_companion, installed by the user, for `video_stream` and HID.
    - _Trade-off:_ depends on private APIs and breaks across Xcode releases. It needs a logged-in macOS user (LaunchAgent), Xcode on the server, and a policy decision on depending on an external native tool.
15. **Agent tools.** `device_list`, `device_open`, `device_screenshot` (MCP image), and `device_close` on the existing `/mcp`, modelled on ref-preview. Gate them behind settings that are off by default, as ref-preview does.

### Open questions for the user

1. **Default link target.** Should BiBCode keep chat's current "internal browser by default" and extend it to the terminal? Or should it match Orca and ref-preview ("system" by default, with a setting, and a first-click prompt like Orca's)?
2. **Terminal file paths.** Should `.html`/`.pdf` paths in the terminal open in the browser by default, with other paths going to the editor?
3. **Remote reach.** Gateway only (b), gateway plus SSH `-L` (d), or invest in SOCKS profiles (a)? Is the origin change acceptable for your typical dev servers and OAuth flows?
4. **Gateway origin model.** A second listener port (an extra SSH `-L` and relay ingress) or wildcard subdomains (wildcard DNS and certificates on the relay)?
5. **Browser mode.** Should web clients get a gateway-backed preview, either a top-level tab or a sandboxed iframe on the gateway origin, or does the browser stay desktop-only?
6. **Linux.** Fix child-webview positioning (`gtk::Fixed`) now, or hide the preview on Linux until upstream fixes it?
7. **Emulators.** Is Android-first acceptable? For iOS, may BiBCode depend on idb_companion's private-API HID, or should iOS be limited to view-only (screenshots and `openurl`) without input?
8. **Media transport.** Is a dedicated binary media WebSocket acceptable as an exception to typed RPC, or must frames stay inside RPC (base64, ≤ 1/RTT fps)?
